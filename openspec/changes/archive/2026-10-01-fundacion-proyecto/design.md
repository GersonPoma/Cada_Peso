# Design

## Context

El repositorio está vacío salvo por `openspec/` (ver proposal.md - Why). No hay backend, frontend, ni convenciones documentadas. Este diseño cubre cómo generar y configurar el monorepo (`/backend`, `/frontend`), cómo dejar lista la infraestructura transversal del backend (entidad base, excepciones, seguridad JWT, mapeo) sin construir todavía ninguna feature de negocio, y cómo documentar las convenciones para que los changes futuros (auth, cuenta, categoria, transaccion) las sigan sin repetir decisiones.

Restricciones dadas por el usuario: Spring Boot 4 + Java 21 + Maven, Angular estable con standalone components + signals, PostgreSQL, dinero en milésimas como `long`, JWT, organización por feature, specs futuras con escenarios Dado/Cuando/Entonces, commits convencionales en español.

## Goals / Non-Goals

**Goals:**
- Dejar un backend que compila, arranca en el puerto 8080, se conecta a PostgreSQL y expone `/actuator/health` en `UP`.
- Dejar un frontend que compila y arranca con `ng serve` en el puerto 4200, con `core/`, `shared/`, `features/` ya creadas y apuntando al backend.
- Dejar la infraestructura transversal del backend lista para que la primera feature de negocio (presumiblemente `auth`) solo tenga que añadir su propio paquete: `EntidadBase`, jerarquía de excepciones + `ManejadorGlobalExcepciones`, convenciones de DTO/mapper, y un `SecurityConfig` stateless que ya protege todo salvo `/actuator/health` y `/api/v1/auth/**` (sin filtro JWT ni endpoints de login todavía).
- Documentar las convenciones en `AGENTS.md`/`CLAUDE.md` y en `openspec/config.yaml` (`context` + `rules`) para que sean la fuente de verdad para changes futuros.

**Non-Goals:**
- No se implementa ninguna feature de negocio (sin entidades `Cuenta`, `Categoria`, `Transaccion`, sin endpoints de autenticación funcionales, sin login real).
- No se configura CI/CD, Docker, ni despliegue.
- No se eligen ni implementan migraciones (Flyway/Liquibase quedan explícitamente excluidas; el esquema lo gestiona Hibernate).
- No se escriben tests de negocio (no hay negocio todavía); solo se deja la infraestructura de test lista (dependencias, builders base si aplican).

## Decisions

**Generación con Spring Initializr real, no plantilla manual.**
Se genera `/backend` con start.spring.io (vía `curl` al endpoint de Initializr o la web) usando exactamente: Maven, Java 21, Spring Boot 4 (última estable), packaging jar, `groupId=com.presupuesto`, `artifactId=backend`, paquete base `com.presupuesto`, dependencias `web, security, data-jpa, postgresql, lombok, validation, actuator`. Alternativa descartada: escribir el `pom.xml` a mano — se descarta porque Initializr garantiza versiones compatibles entre Spring Boot 4, Java 21 y los starters, evitando desalineaciones de versión.

**MapStruct + Lombok vía `lombok-mapstruct-binding`, con orden de annotation processors explícito.**
Se añade `org.mapstruct:mapstruct`, `org.mapstruct:mapstruct-processor`, y `org.projectlombok:lombok-mapstruct-binding` al `pom.xml`, y se configura `maven-compiler-plugin` con la lista de `annotationProcessorPaths` en orden: `lombok`, `lombok-mapstruct-binding`, `mapstruct-processor`. Razón: sin el binding y sin este orden, Lombok genera los getters/setters después de que MapStruct los necesita, rompiendo el mapeo en tiempo de compilación.

**JWT con la librería `jjwt` (io.jsonwebtoken), no Spring Security OAuth2; `SecurityConfig` stateless desde la fundación, sin filtro JWT todavía.**
Se añaden `jjwt-api`, `jjwt-impl`, `jjwt-jackson` al `pom.xml` para que el change de `auth` los use directamente. En este change se crea únicamente `SecurityConfig` en `comun/seguridad`: un `SecurityFilterChain` con `SessionCreationPolicy.STATELESS` y CSRF deshabilitado (no aplica a una API stateless sin cookies de sesión), que permite sin autenticación `/actuator/health` y `/api/v1/auth/**` (reservado para los futuros endpoints de login/registro) y exige autenticación (`anyRequest().authenticated()`) en el resto. No se agrega el filtro de validación de JWT ni un `AuthenticationProvider` todavía — eso es trabajo del change de `auth`; hasta entonces, cualquier ruta protegida devuelve 401 por falta de autenticación, que es el comportamiento fail-closed esperado. Alternativas descartadas: Spring Authorization Server (mucho más pesado que lo que pide un JWT simple stateless para una app monolítica); no crear `SecurityConfig` todavía y dejar todo abierto (fail-open, deja cualquier endpoint futuro sin protección hasta que `auth` configure seguridad).

**`SecurityConfig.exceptionHandling` con `AuthenticationEntryPoint`/`AccessDeniedHandler` propios, devolviendo el mismo formato `ProblemDetail` que `ManejadorGlobalExcepciones`.**
`@RestControllerAdvice` solo captura excepciones lanzadas dentro del dispatcher de Spring MVC; las excepciones de autenticación/autorización se lanzan en la cadena de filtros de Spring Security, antes de llegar al dispatcher, así que `ManejadorGlobalExcepciones` nunca las ve. Por eso `SecurityConfig` configura `exceptionHandling` con dos componentes propios en `comun/seguridad`: un `AuthenticationEntryPoint` que responde 401 y un `AccessDeniedHandler` que responde 403, ambos construyendo manualmente un `ProblemDetail` con los mismos campos que `ManejadorGlobalExcepciones` (`codigo`, `timestamp`, sin stack trace), usando los nuevos códigos `CodigoError.NO_AUTENTICADO` y `CodigoError.ACCESO_DENEGADO` respectivamente. Alternativa descartada: dejar los handlers por defecto de Spring Security (401/403 con cuerpo vacío o HTML) — se descarta porque rompería la consistencia de formato de error que el resto de la API expone vía RFC 9457.

**`EntidadBase` abstracta con `@MappedSuperclass`, no `@Inheritance` de tabla única/joined.**
Decisión ya fijada por el usuario; se documenta la razón: cada entidad de negocio necesita su propia tabla (una tabla por feature), y `@MappedSuperclass` evita una tabla compartida de herencia que no aporta valor aquí. `equals`/`hashCode` se escriben a mano (basados en `id`, con hashCode constante por clase) porque el `equals`/`hashCode` generado por Lombok falla con proxies de Hibernate (lazy loading) y con colecciones antes de persistir.

**Excepciones de negocio como jerarquía propia + `ProblemDetail`, no `@ExceptionHandler` por controller.**
Un `@RestControllerAdvice` único (`ManejadorGlobalExcepciones`) centraliza el mapeo de excepciones a RFC 9457. El enum `CodigoError` incluye, además de los códigos de negocio, `NO_AUTENTICADO` y `ACCESO_DENEGADO` — estos dos no los usa `ManejadorGlobalExcepciones` sino el `AuthenticationEntryPoint`/`AccessDeniedHandler` de `SecurityConfig` (ver decisión de seguridad arriba), para que todos los códigos de error de la API, vengan del dispatcher o de los filtros de seguridad, vivan en un único enum. Alternativa descartada: manejar excepciones dentro de cada controller — se descarta porque duplicaría lógica de formato de error en cada feature futura.

**Valores por defecto de conexión a PostgreSQL: base `presupuesto`, usuario `postgres`, puerto `5432`, vía variables de entorno `DB_HOST`/`DB_PORT`/`DB_NAME`/`DB_USER`/`DB_PASSWORD`.**
`application.properties` lee la conexión de estas cinco variables de entorno, las cinco con valor por defecto local (`DB_HOST=localhost`, `DB_PORT=5432`, `DB_NAME=presupuesto`, `DB_USER=postgres`, `DB_PASSWORD=admin`, vía la sintaxis `${DB_PASSWORD:admin}` igual que el resto), para que cualquier desarrollador con una instancia local estándar de PostgreSQL pueda levantar el backend sin configuración adicional, incluida la contraseña. Los nombres exactos de estas variables y sus defaults se documentan también en `AGENTS.md`, para que los changes futuros (y cualquier entorno distinto del local) los reutilicen en vez de inventar otros nombres.

**Dinero como `long` en milésimas desde el día uno de la infraestructura.**
Aunque no hay entidades de negocio todavía, esta convención se documenta en `AGENTS.md` y se refleja en el pipe de moneda del frontend (`shared/`) para que la primera feature que use dinero (`cuenta`, `transaccion`) no tenga que decidir esto de nuevo.

**Angular 21 con standalone components + signals, sin NgModules.**
Se usa `npx @angular/cli@21 new frontend --routing --style=scss --ssr=false --skip-git --defaults` con la configuración moderna por defecto de Angular (standalone), routing propio, SCSS, sin SSR. `core/`, `shared/`, `features/` se crean como carpetas simples (no librerías de workspace) para mantener el setup simple en esta etapa fundacional. Se fija la versión mayor (`@21`) en lugar de `@latest` porque la línea `22.x` de Angular CLI exige Node.js `^22.22.3` y el entorno de desarrollo tiene Node `22.20.0`; antes de generar el proyecto se verifica la compatibilidad real (`npm view @angular/cli@<major> engines`) en vez de asumirla. Angular 21 también cambia por defecto a Vitest como test runner (en vez de Karma/Jasmine) y genera `.prettierrc` directamente (en vez de una clave `"prettier"` en `package.json`); ambos son aceptados tal como los genera el CLI, sin configuración adicional en este change. Angular CLI también genera su propio `.editorconfig` dentro de `/frontend` con `root = true`, que se elimina junto con el `.gitignore` generado (ver decisión de `.editorconfig` más abajo), porque `root = true` corta la cascada de EditorConfig e ignoraría silenciosamente el límite de 100 columnas de la raíz para todo el frontend.

**Conexión frontend→backend vía proxy de desarrollo de Angular CLI (`proxy.conf.json`), sin CORS en el backend.**
Los `environments` del frontend usan la URL base de la API como ruta **relativa** (`/api/v1`), nunca absoluta (`http://localhost:8080/api/v1`): si el frontend llamara directo al host:puerto del backend, el navegador haría una petición cross-origin (4200 → 8080) que exigiría CORS. En su lugar, `proxy.conf.json` mapea `/api` → `http://localhost:8080` y se referencia desde `angular.json` (`projects.frontend.architect.serve.options.proxyConfig`), de modo que `ng serve` reenvíe las peticiones al backend como same-origin desde la perspectiva del navegador. No se configura CORS en el backend en este change. Alternativa descartada: URL absoluta + CORS habilitado en el backend — se descarta porque añade superficie de configuración de seguridad (orígenes permitidos) que no hace falta mientras frontend y backend se sirven juntos en desarrollo; se reconsiderará si en el futuro se despliegan en orígenes distintos sin proxy.

**`.editorconfig` único en la raíz + Prettier en el frontend, límite de línea de 100 columnas en todo el monorepo.**
`.editorconfig` en la raíz fija UTF-8, fin de línea LF, indentación de 4 espacios para Java y 2 espacios para TS/HTML/SCSS/JSON, y `max_line_length = 100`, para que cualquier editor respete el mismo estilo sin depender de que cada IDE esté configurado manualmente. Debe ser el único `.editorconfig` del monorepo: el `.editorconfig` que `ng new` genera dentro de `/frontend` (con `root = true` y sin `max_line_length`) se elimina tras generar el proyecto, igual que su `.gitignore`, para que no corte la cascada de EditorConfig e ignore silenciosamente el límite de 100 columnas en todo el frontend. En `/frontend` se configura Prettier con `printWidth: 100` (mismo límite que `.editorconfig`) y `singleQuote: true`, en una única configuración: si Angular CLI ya generó una clave `"prettier"` en `package.json`, se actualiza ahí; si generó `.prettierrc` (como hace Angular 21 por defecto) o no generó ninguna, se usa o crea `.prettierrc`. Nunca coexisten ambas, para evitar que dos configuraciones de Prettier den resultados distintos. No se configura un formateador equivalente para Java en este change (p. ej. Spotless/Checkstyle) — `.editorconfig` alcanza para que los IDEs sugieran el límite; forzarlo en build queda como mejora futura si se añade CI. Esta convención se documenta en `AGENTS.md` y en el `context` de `openspec/config.yaml` para que los changes futuros la respeten.

**`openspec/config.yaml` como fuente de verdad para `context` y `rules`, `AGENTS.md`/`CLAUDE.md` como fuente de verdad para humanos y agentes dentro del código.**
`config.yaml` alimenta los workflows de OpenSpec (propone, aplica, etc.) con el stack y las convenciones, y define la regla de que las specs futuras usen escenarios Dado/Cuando/Entonces. `AGENTS.md` es la referencia completa y detallada de convenciones (nomenclatura, estructura, reglas de código) que cualquier agente o desarrollador debe leer antes de tocar el código; `CLAUDE.md` simplemente lo importa con `@AGENTS.md` para no duplicar contenido.

## Risks / Trade-offs

- [Spring Boot 4 es relativamente nueva; puede haber incompatibilidades de starters/versiones de terceros (MapStruct, jjwt) no probadas todavía] → Fijar versiones compatibles conocidas en el `pom.xml` generado y verificar con un build limpio (`mvnw.cmd clean verify` en Windows) antes de cerrar el change.
- [`ddl-auto=update` sin migraciones puede generar drift de esquema no controlado a medida que crezcan las entidades] → Aceptado conscientemente por el usuario para esta etapa; se documenta en `AGENTS.md` como decisión explícita, revisable si el proyecto introduce un pipeline de CI/CD más adelante.
- [`SecurityConfig` deja todo protegido por defecto (fail-closed) sin que exista todavía login ni filtro JWT, lo que puede bloquear pruebas manuales de endpoints futuros hasta que el change de `auth` añada la autenticación] → Aceptado como comportamiento esperado: es más seguro que fail-open; `/actuator/health` y `/api/v1/auth/**` quedan abiertos para health checks y para los futuros endpoints de login/registro.
- [Dejar la infraestructura de seguridad JWT "esqueleto" sin endpoints de login puede dar una falsa sensación de que la autenticación ya funciona] → `AGENTS.md` y el proposal dejan explícito que no hay feature de auth funcional todavía; la verificación de este change se limita a arranque + health check, no a login.
- [Generar los proyectos con las herramientas oficiales (Initializr, Angular CLI) depende de tener red/Node/CLI disponibles en el entorno de ejecución] → Si la generación automática falla, se documenta como bloqueador y se reintenta o se construye manualmente replicando exactamente la misma configuración (groupId, dependencias, versiones).
- [La última versión mayor de Angular CLI puede exigir una versión de Node.js más nueva que la instalada en el entorno de desarrollo (ocurrió al pasar de Angular CLI 20 a 21: la línea `22.x` requiere Node `^22.22.3`, no satisfecho por el Node `22.20.0` instalado)] → Antes de generar o regenerar `/frontend`, verificar la compatibilidad real (`node -v` y `npm view @angular/cli@<major> engines`) y fijar la versión mayor de Angular CLI más reciente que sea compatible con el Node.js instalado, en vez de usar `@latest` a ciegas.
- [`.editorconfig` y Prettier no se aplican automáticamente en CI (no hay CI en este change), así que nada impide en build que se viole el límite de 100 columnas] → Aceptado para esta etapa; si se añade CI en el futuro, se puede agregar un step que ejecute `prettier --check` y un formateador equivalente para Java (Spotless/Checkstyle).

## Migration Plan

No aplica migración de datos (proyecto greenfield, sin datos previos). El plan de despliegue de este change es puramente de puesta en marcha local:
1. Generar `/backend` y `/frontend`, y la estructura de paquetes/carpetas acordada.
2. Configurar `application.properties` y los `environments` del frontend.
3. Levantar una instancia local de PostgreSQL (o apuntar a una existente vía variables de entorno) y verificar `mvnw.cmd spring-boot:run` (Windows) + `/actuator/health`.
4. Verificar `ng serve` sin errores de compilación.
No hay estrategia de rollback más allá de revertir el commit, ya que no hay sistema en producción todavía.
